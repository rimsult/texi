# Архитектура Texi

> Название продукта — **texi** (раньше Lexi). Внутренние имена пакетов (`@lexi/*`, `lexi_pipeline`,
> база `lexi`, ключи IndexedDB) не менялись, чтобы не ломать сборки и сохранённый прогресс.

## Принципы

1. **Offline-first.** Весь контент — статические JSON-пакеты, которые Service Worker кладёт в precache
   при первом визите. Сервер нужен только для резервной копии прогресса; приложение полностью
   работает без него.
2. **Качество контента проверяется до клиента.** Пайплайн отбрасывает сомнительные вопросы
   (`needs_review`), а ядро повторно валидирует каждый вопрос перед показом.
3. **Ядро не знает о конкретных тренажёрах.** Тренажёр — плагин с фиксированным контрактом;
   движок сессий, планировщик, хранилище и синхронизация от него не зависят.
4. **Синхронизация без конфликтов.** На сервер уходят неизменяемые события ответов с UUID, а не
   состояние. Повторная отправка безопасна (`ON CONFLICT DO NOTHING`), слияние не нужно.

## Компоненты и поток данных

```
 CEFR-J / Octanove ─┐
 WordNet (NLTK) ────┤
 Simple Wiktionary ─┤                         ┌─► apps/web/public/packs/{A1..C2}.json   (общая лексика)
 Wiktionary/WikDict ┼─► data-pipeline (Python) ┼─► apps/web/public/packs/tech-{A1..C2}.json (техническая)
 FrequencyWords ru ─┤   + офлайн-MT en→ru      ├─► manifest.json (schemaVersion 2, наборы `decks`)
 wordfreq ──────────┘   (Argos + WMT19, кеш)   └─► data-pipeline/out/{lexicon,needs_review,skipped,adapt_log}.json
                                                              │
                                                              ▼ seed (при старте API)
 ┌──────────── браузер (PWA) ─────────────┐        ┌──────── apps/api (Fastify) ───────┐
 │ UI (React) ── TrainerRegistry (core)   │        │ POST /v1/sync   ─► attempt_events │
 │      │        TrainingSession (core)   │ events │ GET  /v1/content ◄─ lexemes,      │
 │      ▼        Scheduler/Leitner (core) │ ─────► │                    definitions,   │
 │ IndexedDB: progress · outbox · meta    │  HTTPS │                    questions      │
 │ Service Worker: app shell + все пакеты │        │ PostgreSQL (Supabase / Docker)    │
 └────────────────────────────────────────┘        └───────────────────────────────────┘
```

## Модель контента

Пакет уровня (`packs/B1.json`, технический набор — `packs/tech-B1.json`):

```json
{
  "schemaVersion": 2,
  "deck": "general",
  "level": "B1",
  "entries": [{ "id": "arrive-v", "lemma": "arrive", "pos": "verb", "level": "A2",
                "group": "verb.motion",
                "definitions": [{ "text": "reach a destination", "lang": "en", "source": "wordnet", "quality": 0.9 }],
                "example": "..." }],
  "questions": [{ "trainer": "word-to-definition", "entryId": "...", "lang": "en",
                  "distractors": ["...", "...", "..."],
                  "hard": ["...", "...", "..."] }]
}
```

* `deck`: `general | tech`. У технических слов id с префиксом `tech:` (`tech:transistor-n`) и поле
  `domain` (`it | electrical | physics | math | chemistry | engineering`); прогресс наборов не
  пересекается. Манифест перечисляет наборы (`decks[].levels[]`: файл, хэш, число слов, число
  вопросов `questions` и вопросов со сложным режимом `hard` по `trainer:lang`) и названия областей `fields`.
* `hard` — необязательный список дистракторов для сложного режима (≥ 2, ближайшие первыми);
  `hardGroup` у записи — группа для сложного режима, если отличается от `group`.

* `entries` пакета — слова уровня плюс слова соседних уровней, используемые как дистракторы.
  Клиент загружает пакет выбранного уровня и соседние (±1), объединяя их в `Lexicon`.
* `questions` содержит только прошедшие проверку вопросы (`status = ok`) — от 2 до 5 кандидатов
  в дистракторы; клиент случайно берёт 2 и ещё раз проверяет их правилами из `core/validation.ts`.
* `source`: `simple | wordnet | wiktionary | generated | machine`; у `generated` качество ≤ 0,5
  (ограничение продублировано в БД: `generated_quality_cap`). В пакет попадает **только лучшее
  определение на каждом языке** (то, что покажет клиент).
  * `simple` (0,95) — учебное определение из Simple English Wiktionary («a vehicle with two wheels;
    you use your legs to make it move»). Фразы Cobuild со словом внутри переписаны в словарную форму
    (`rewrite.py`: «If you run, you move very quickly…» → «to move very quickly…»); если не вышло —
    берётся WordNet. Пропусков `___` в определениях нет.
  * `machine` — русское определение, машинный перевод английского (см. ниже).
* `example`, `exampleRu` (перевод примера, только A1–A2), `synonyms` (≤ 3 частотных синонима) —
  показываются после ответа. Пример всегда содержит форму слова (по нему строится «Вставьте слово»).
* Вопрос `trainer: "gap-fill"` дополнительно несёт `span: [start, end]` — где в `example` стоит слово —
  и `forms` — форму ответа и каждого дистрактора в этом месте (`forms[0]` — ответ, дальше по порядку
  `distractors`). В БД — `questions.gap_span`, `questions.gap_forms` (миграция `005_gap_fill.sql`,
  `CHECK`: у gap-fill оба поля есть и длина `forms` = 1 + число дистракторов).
* `translation` (необязательно, только пакеты A1–A2) — короткий перевод слова из Wiktionary;
  ядро кладёт его в `reveal.translation` только для русских вопросов.
* `lang`: `en` на всех уровнях, `ru` — только A1–A2 (пайплайн, `core/policy.ts`, zod-схема API,
  триггер PostgreSQL).
* Манифест технического набора содержит для каждого уровня `fields`: число вопросов по областям
  (клиент показывает, сколько слов доступно в выбранных областях).

### Определения по уровню (`adapt.py`)

Каждое слово получает определение, подходящее **его** уровню:

1. Смысл Simple English Wiktionary сопоставляется со значением WordNet по общим содержательным
   словам (глосса, примеры, синонимы, гиперонимы). В общем наборе слово может перейти на другое
   частотное значение WordNet, если учебное определение описывает именно его (*stop* — «остановка»,
   а не «прекращение»); группа, синонимы, проверки дистракторов и перевод следуют за значением.
   Технические термины сохраняют закреплённое техническое значение (нужна явная пометка области
   или ≥ 2 общих слова).
2. «Стоимость» определения для учащегося = сумма превышений уровня по всем содержательным словам
   (уровень слова — из CEFR-списков, иначе по частотности) + штраф за длину > 14 слов.
3. A1–B1 берут учебное определение, если оно не заметно сложнее; B2 — более лёгкое из двух;
   C1–C2 — точную глоссу WordNet, если учебное не намного проще.
4. Решения записываются в `out/adapt_log.json`; в статистике сборки — доля слов выше уровня по уровням
   (`readability_wordnet:*` до и `readability:*` после).

### Русские определения (`mt.py`)

Офлайн, без API и LLM: два независимых движка — Argos Translate en→ru 1.9 (CTranslate2) и
Facebook FAIR WMT19 en→ru (transformers, CPU). Каждый даёт несколько гипотез (beam search), затем
**каждый движок оценивает каждого кандидата** — свои и чужие (средняя лог-вероятность токена при
принудительном декодировании, `score()` у бэкенда), и выигрывает кандидат с наибольшей суммой
(ансамблевое переранжирование). Ошибку одной модели — галлюцинацию («concerts» → «консилиумах»),
обрезанный хвост или потерянное второе предложение — вторая модель считает маловероятной. Сверху —
небольшие поправки: правильная форма (инфинитив, прилагательное), перевод слова из Wiktionary
(глоссарий), штраф за повтор корня («планеты с планетами»). Кандидат, потерявший предложение или сжавший определение из трёх слов в одно («day after today» → «послезавтра»), проигрывает полному; выдуманный пол («мужчина женского пола») отбраковывается; «приятное, приятное» склеивается в одно слово. Гипотезы WMT19 без `</s>` (упёрлись в
лимит длины) отбрасываются. У WMT19 в чекпойнте только английские BPE-правила, поэтому русский текст
режется на минимальное число токенов словаря (совпадает с собственной токенизацией модели в ~80 %
предложений). Без функции `score` (например, DeepL) работает консенсус по chrF. Строгие проверки
(только кириллица, без повторов, разумная длина). Переводятся учебные определения (без маски) и
примеры A1–A2. Необязательно — DeepL (`DEEPL_AUTH_KEY`). Кеш `data/mt_en_ru.json` в репозитории:
сборка без моделей использует только его.

### Как пайплайн выбирает дистракторы

Кандидат отклоняется, если: другая часть речи; уровень дальше ±1; та же семантическая группа;
синоним или общий синсет WordNet; общий русский перевод; сходство Wu-Palmer ≥ 0,8; одно слово
содержит другое; определение кандидата «подсказывает» ответ. Для русских вопросов — ещё и
`ru_definition_mentions_translation`: русское определение одного слова содержит (форму) перевода
другого («молодая собака» рядом с *dog*). Слова из `text.SENSITIVE` (ругательства, сексуальная
и оскорбительная лексика) изучаются как ответы, но никогда не бывают неверными вариантами
(`sensitive_word`). Отбор детерминирован: кандидаты перебираются в порядке
`stable_order` — хеш crc32 пары «вопрос | кандидат», поэтому добавление или удаление слов не
перемешивает остальных кандидатов (стабильные сборки, воспроизводимые тесты, кеш GapLM остаётся
действительным). Если подходящих кандидатов меньше двух, вопрос получает
`needs_review` с причиной и никогда не попадает в пакеты.

Сложный режим (`hard_pool`) работает наоборот: кандидат обязан быть из **той же** группы
(`hard_group`: lexname WordNet для существительных и глаголов, семья антонимов кластера для
прилагательных, у наречий — по прилагательному). Отклоняются: синонимы, общие значения и
переводы, гиперонимы/гипонимы, одинаковые определения, «подсказки» в определении и слишком
близкие пары (Wu-Palmer ≥ 0,93, у глаголов ≥ 0,83). Кандидаты сортируются по близости, и каждый
следующий проверяется ещё и против уже выбранных (`clashes_with_chosen`), чтобы два неверных
варианта не совпадали между собой. Клиент берёт 2 случайных из 3 ближайших, проверяет их тем же
`checkPackQuestion(…, "hard")` и добавляет к id вопроса суффикс `:hard`.

Технический набор (`technical.py`): кандидаты из тематических меток WordNet, помет области
Wiktionary и гипонимов технических корневых понятий (только основное значение слова) → стоп-лист
и порог частотности wordfreq → уровень из CEFR-списков или по частотности (пороги откалиброваны
на CEFR) → определение технического значения; перевод слова берётся, только если значение в
Wiktionary совпадает с техническим (`pick_tech_sense`: пересечение основ слов, бонус за помету
области). Ядро области гарантирует список `SEEDS` (~390 терминов с закреплённым синсетом), они
имеют приоритет над правилами. Дистракторы — из того же набора по тем же правилам.

Расширение общего набора (`extra.py`): леммы WordNet вне CEFR-списков с Zipf ≥ 2,8 и счётчиком
SemCor ≥ 2 (или ≥ 1 при Zipf ≥ 3,2); без имён собственных и омонимов имён, форм известных слов,
помет usage-domain (сленг, грубое, устаревшее, торговые марки…) и стоп-листа; одна часть речи на
слово; уровень по частотности, не ниже B2.

## Ядро (`packages/core`)

| Модуль | Назначение |
|---|---|
| `types.ts`, `policy.ts` | уровни, языки, разрешённые языки по уровню, соседние уровни |
| `lexicon.ts` | индекс слов, выбор лучшего определения с учётом языка и качества |
| `validation.ts` | правила дистракторов на клиенте (вторая линия защиты) |
| `trainer.ts` | контракт `TrainerPlugin`, общий тип `McqQuestion` |
| `trainers/meaningChoice.ts` | два готовых тренажёра: слово → определение, определение → слово; учитывают `ctx.difficulty`, язык сессии (`sessionLang`) и выбранные области `ctx.domains` (слова и, если хватает, варианты — из этих областей); у каждого варианта `explain` (чьё это определение / что значит слово), в `reveal` — перевод, пример с переводом, синонимы, оригинал |
| `trainers/gapFill.ts` | дополнительный тренажёр «Вставьте слово»: пример с пропуском, варианты в той же грамматической форме; `checkGapQuestion` перепроверяет span, формы и дистракторы; «a/an» перед пропуском не выдаёт ответ |
| `registry.ts` | `TrainerRegistry`: основные (`tier: "main"`) и дополнительные (`tier: "extra"`) тренажёры, заглушки «Скоро» (аудирование, грамматика) |
| `scheduler.ts` | интервальное повторение по Лейтнеру: 6 коробок (0 · 10 мин · 1 · 3 · 7 · 21 день); коробка ≥ 4 — «выучено» |
| `session.ts` | `TrainingSession`: последовательность вопросов, проверка, события `AttemptEvent` |

Прогресс хранится **отдельно для каждого тренажёра** (`progress[trainerId, entryId]`): знание
слова «в одну сторону» не засчитывается в другую.

## Клиент (`apps/web`)

* `services/content.ts` — загрузка манифеста и пакетов (из precache при офлайне), отдельный
  `Lexicon` для каждого набора.
* `services/embedded.ts` + плагины в `standalone.ts` — однофайловая сборка (`vite build --mode
  standalone`): пакеты встраиваются как gzip+base64 и отдаются через подменённый `fetch`
  (`DecompressionStream`), JS/CSS/шрифты/иконка инлайнятся в `Texi.html`, Service Worker не
  регистрируется, API отключён (`sync: disabled`). Если IndexedDB недоступен (некоторые браузеры
  для `file://`), используется хранилище в памяти.
* `services/store.ts` + `db.ts` — IndexedDB: `progress`, `outbox` (неотправленные события), `meta`
  (deviceId, настройки: тренажёр, набор, уровень, сложность, язык, длина). Запись ответа и
  обновление прогресса — одна транзакция. Событие `AttemptEvent` содержит `deck` и `difficulty`.
* `services/sync.ts` — `SyncManager`: отправка батчами по 200, подтверждение `accepted + duplicates +
  rejected` (невалидное событие сервер отклоняет отдельно — оно удаляется и не блокирует очередь; если
  сервер не подтвердил ничего, цикл останавливается и уходит в backoff),
  состояния `idle | syncing | offline | error | disabled`, экспоненциальный backoff, запуск по
  событию `online`, по таймеру и после каждого ответа.
* `ui/renderers.ts` — соответствие `question.kind` → React-компонент.
* `i18n/` — строки интерфейса на русском и английском (`STRINGS.ru | en`, `useT()`); язык
  интерфейса (`settings.uiLang`) не зависит от языка определений и хранится в настройках.

## Сервер (`apps/api`)

* `Repository` — интерфейс; реализации `PgRepository` (продакшен) и `MemoryRepository`
  (разработка, E2E); HTTP-слой тестируется с обеими.
* Миграции — SQL-файлы в `migrations/`, применяются при старте (`AUTO_MIGRATE`).
  `002_decks_hard_mode.sql`: `lexemes.deck/domain/hard_group` (проверка префикса `tech:`),
  `questions.hard_distractors` (0 или ≥ 2), `attempt_events.deck/difficulty`.
* Сидинг — при старте, если версия контента в БД отличается от версии пакетов (`AUTO_SEED`).
  Миграции и сидинг идут под `pg_advisory_lock` (`withStartupLock`): одновременно стартующие
  экземпляры выполняют их по очереди. Ошибки простаивающих соединений пула логируются, а не роняют процесс.
* `/v1/sync` проверяет конверт целиком (deviceId, 1–500 событий с UUID — иначе 400), а события — по
  одному: валидные сохраняются, id невалидных возвращаются в `rejected`.
* Из БД можно собрать пакет, идентичный статическому (`/v1/content/packs/:level?deck=tech`) —
  задел для будущего редактирования контента через админку.

## Как добавить новый тренажёр

Живой пример — «Вставьте слово» (`gap-fill`). Ядро, сессия, планировщик, хранилище и синхронизация
при его добавлении не менялись.

1. **Плагин в ядре** — `packages/core/src/trainers/gapFill.ts` реализует `TrainerPlugin<McqQuestion>`:
   `items(ctx)` — слова уровня, у которых есть вопрос `gap-fill`; `build(entryId, ctx)` — собрать
   вопрос (вернуть `null`, если он не прошёл `checkGapQuestion`); `check` — сравнить ответ.
   Метаданные плагина: `tier: "extra"` (раздел «Дополнительно» на главной), `questionLang: "en"`
   (вопросы всегда английские, счётчики берутся по ключу `gap-fill:en`), `supportsHard: false`
   (один уровень сложности — переключатель скрыт).
2. **Регистрация** — `createDefaultRegistry()` в `registry.ts` (`registry.register(createGapFillTrainer())`).
3. **Рендерер** — вопрос того же вида `mcq`, поэтому используется `McqCard`: `prompt.style: "sentence"`
   и `prompt.gap` (`before`, `after`, `answer`) — карточка рисует пропуск, а после ответа вставляет слово.
   Иначе — свой компонент и строка в `RENDERERS` (`apps/web/src/ui/renderers.ts`).
4. **Контент** — `data-pipeline/lexi_pipeline/gapfill.py`: `find_gap` (ровно одно вхождение формы
   слова, ≥ 4 слов, тег формы по контексту: *has eaten* → VBN, *apples* → NNS, *bigger* → JJR),
   `inflect` (дистрактор в той же форме по lemminflect, только реальные формы по wordfreq; без
   «beautifuler», «more big», «informations»), `rejection_reason` (правила дистракторов + семья
   антонимов прилагательных) и `GapLM` — проверка маскированной языковой моделью BERT: дистрактор,
   который тоже подходит в пропуск, отклоняется. Вердикты кешируются в `data/gap_lm.json`.
5. **Тесты** — юнит-тесты плагина (`packages/core/test/gapFill.test.ts`), пайплайна
   (`tests/test_gapfill.py`), проверка реальных пакетов (`realPacks.test.ts`, `test_pack_contract.py`),
   схема БД (`pg.test.ts`), компоненты (`app.test.tsx`, `mcqCard.test.tsx`) и E2E-сценарий.

### Проверка «Вставьте слово» языковой моделью (`GapLM`)

BERT base uncased (Apache 2.0, маскированная модель, не генеративная) оценивает, насколько слово
подходит в пропуск: однословная часть — вероятность в одной позиции `[MASK]`, слово из k ≤ 3 частей —
среднее по k маскам (завышенная оценка: длинный дистрактор скорее отклонится); у ответа —
среднее лог-правдоподобие частей слева направо. Сырые вероятности любят частые слова, поэтому
сравнивается и «подходящесть» p(слово | пропуск) / p(слово) (частотность — wordfreq). Дистрактор
отклоняется, если его подходящесть ≥ 1/1000 подходящести ответа, или вероятность ≥ 1/100
вероятности ответа, или ≥ 0,01 сама по себе («I ate an ___ for lunch»: *orange*, *egg* — нет;
*river*, *song* — да). Пороги подобраны на выборке из 400 предложений (`probe/gap_calibrate.py`,
`probe/gap_rules.py`). Наречия в тренажёр не берутся: почти любое наречие грамматически подходит
(«The judge sat there ___»).

Кеш хранит для каждого предложения вероятность ответа и вердикты по кандидатам, которые реально
перебирает сборщик вопроса (в его детерминированном порядке, пока не набрано 10 принятых, но не
больше 200 кандидатов на предложение — там, где подходит почти любое слово, дальше искать бесполезно):
`x` — отклонённые, `ok` — принятые. Кандидат без вердикта в проверенном предложении считается
отклонённым, поэтому сборка без модели (`--no-translate`) повторяет вопросы в точности.
Предложение, которое модель не видела, остаётся непроверенным (`questions_gap_fill_lm_unchecked`
в статистике сборки). Модель проверяет кандидатов раундами, пока запросов не останется
(`gap_lm_pending: 0`; следующая сборка ничего не спрашивает), и обоих наборов *до* построения любых вопросов
(у общего и технического набора есть общие примеры), а в конце полной сборки `GapLM.prune()`
удаляет вердикты, которые ни один вопрос больше не запрашивал (кеш ~2,6 МБ, ~6 000 предложений).
Сборка с моделями и сборка без них (`--no-translate`) дают побайтно одинаковые пакеты (`PYTHONHASHSEED=0`
выставляется самой сборкой: от него зависит порядок связей в NLTK).

Тест `registry.test.ts` («runs a new plugin through the unchanged session engine») показывает, что
сторонний плагин работает с движком без изменений в ядре.

## Решения

| Решение | Почему |
|---|---|
| Статические пакеты вместо API-запросов за словами | офлайн с первого визита, бесплатный CDN Vercel, нет нагрузки на free-tier сервер |
| Лог событий вместо синхронизации состояния | нет конфликтов слияния, повторы безопасны, прогресс восстанавливается из событий |
| Анонимный `deviceId` вместо регистрации | требование MVP; позже устройство привязывается к аккаунту |
| Строгие шаблоны вместо LLM | бюджет 0, предсказуемость, тестируемость; сгенерированное помечено и имеет низкое качество |
| Fastify + `pg` без ORM | минимум зависимостей, быстрый холодный старт на Render Free |
| Дублирование правил (пайплайн + ядро + БД) | ошибку в одном слое ловит следующий; каждый слой покрыт своими тестами |
| Наборы слов как отдельные пакеты (`tech-*.json`) | технический набор не утяжеляет общий, прогресс и статистика не смешиваются, новый набор добавляется без изменения ядра |
| Сложный режим — отдельный список `hard`, а не другой алгоритм на клиенте | все проверки близости (WordNet, переводы) остаются в пайплайне; клиент только выбирает и перепроверяет |
| Однофайловая сборка из того же кода | один UI и одна логика для PWA и `Texi.html`; отличия только в источнике пакетов и отключённой синхронизации |
| Учебные определения Simple English Wiktionary, а не Cambridge/Oxford | словари для учащихся Cambridge и Oxford проприетарны; Simple Wiktionary — открытый (CC BY-SA) и написан базовой лексикой; выбор по измеряемой «стоимости», а не вручную |
| «Вставьте слово» проверяется маскированной моделью, а не LLM | BERT бесплатен, работает офлайн на CPU только при сборке, вердикты детерминированы и закешированы; клиент получает готовые варианты |
| Два офлайн-переводчика с взаимной оценкой гипотез | бесплатно и воспроизводимо; независимые модели редко ошибаются одинаково: обрезанный или выдуманный перевод одной модели маловероятен для другой, поэтому сумма оценок надёжнее лучшей гипотезы одной модели и надёжнее простого «согласия» (chrF) |
